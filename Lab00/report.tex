\subsection{NUMA architecture (Question 3)}
% --------------------------------------------------

NUMA means Non-Uniform Memory Access, access time depends on which socket owns the memory. \textbf{boada-18} has two sockets, and each socket has its own memory bank (about 62–64 GB). Any core can access any byte of the full 123 GB, but the path differs. When core 0 (socket 0) reads from the memory physically attached to socket 0, it goes directly through the local memory controller. When it reads from socket 1 memory, the request crosses the inter-socket link. That extra hop costs time. \\

These are relative costs defined by the ACPI SLIT. The value 10 is the baseline (local) and 20 is the cost of reaching the other socket's memory. The distance matrix is shown in Table~\ref{tab:numa-distance}.

\begin{table}[H]
\centering
\begin{tabular}{c|cc}
	
 & \textbf{Node 0} & \textbf{Node 1} \\
\midrule
	\textbf{Node 0} & 10 & 20 \\
	\textbf{Node 1} & 20 & 10 \\
\bottomrule
\end{tabular}
\caption{NUMA distance matrix obtained with \texttt{numactl} on boada-18.}
\label{tab:numa-distance}
\end{table}

The ratio is \textbf{1:2}, which means that accessing memory on the other socket is twice as expensive as accessing local memory.

\subsection{OpenMP scaling (Question 3)}
% --------------------------------------------------

{\bfseries Strong scaling}: fixed problem size, varied threads. Ideal speedup = $p$. T(1)~1.45s, speedup~31 at 32 threads, efficiency~0.97. The measured speedup tracks the ideal line almost perfectly up to 32 threads. \\
{\bfseries Weak scaling}: the problem grows proportionally with the number of threads. The ideal is constant execution time, corresponding to efficiency 1; the measurements remain close to 0.99. \\

% The excellent scaling is expected because iterations are independent, the reduction is the only shared result, and the loop has a balanced cyclic distribution. The computation mostly uses registers, so memory traffic and synchronization are limited.

Beyond 32 threads: \textbf{boada-18} has 32 physical cores. Threads 33-64 land on hyperthreads (two threads sharing one core). Performance gain decreases because two threads compete for the same execution resources.

The 64-thread strong-scaling run confirms this effect. The time decreases from $0.047641$ s with 32 threads to only $0.048317$ s with 64 threads in the recorded run, while the speedup changes from about $30.82$ to $30.39$. Thus, the 64-thread run is slightly slower than the 32-thread run (0.0483 s vs 0.0476 s). Adding 32 hyperthreads to 32 already-busy physical cores creates contention for execution units and actually hurts performance.

\subsubsection{MPI strong scaling (1--32 processes)}

The MPI implementation scales almost linearly from 1 to 16 processes. The 16-process run takes $0.752$ s and gives a speedup of $14.69$ relative to the sequential baseline. The apparent gap from ideal scaling is partly due to the baseline mismatch: one MPI process takes $11.79$ s, whereas the sequential program takes $11.05$ s. Relative to the one-process MPI run, the 16-process efficiency is approximately $0.98$.

The time improves slightly at 17 processes but rises from $0.741$ s to $0.758$ s at 18 processes. This transition is consistent with the node topology: each socket has 16 physical cores, so the node has 32 physical cores across two sockets. If the job scheduler placed all processes on a single socket (16 cores, 32 logical CPUs via hyperthreading), processes beyond 16 would share physical cores.

From 19 to 32 processes, execution time decreases again, but the final speedup is $25.40$ rather than the ideal 32, giving an efficiency of about $0.79$ relative to the sequential program. Communication is not the main bottleneck because the program performs only one reduction of a single accumulated value after the computation.

For the same 32 workers, the hybrid configuration with two MPI processes and 16 OpenMP threads per process is faster ($0.373$ s) than 32 MPI processes ($0.435$ s). The hybrid run gives each process 16 threads on a different node, avoiding the process oversubscription and placement effects that appear when many MPI processes share a node.

With two nodes and 64 total OpenMP threads, the hybrid run takes $0.187$ s. Its speedup over the sequential baseline is $11.05/0.187 \approx 59.07$, corresponding to an efficiency of approximately $0.92$. This differs from the single-node OpenMP 64-thread result because the hybrid run uses 64 physical cores across two nodes, whereas one node provides only 32 physical cores and uses hyperthreads for threads 33--64.

The one-node hybrid experiment was not recorded in the available job output. Both ranks in the available run executed on boada-18 and boada-19, so no measured time, speedup, or efficiency can be reported honestly for the requested one-node configuration. Based on the hardware and the OpenMP 64-thread result, it would be expected to flatten after 32 physical cores because $2\times32$ threads would share the node's 32 cores.
